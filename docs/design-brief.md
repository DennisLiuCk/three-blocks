# Three Blocks — 設計簡報

> 本文件記錄專案啟動時定下的方向與原則,目的是先做出第一個能玩的版本,而不是一開始就把所有東西定死。

## 技術決策

- 引擎:Godot(GDScript)。
- 架構:邏輯與呈現分離,而不是前後端分離——規則跟呈現拆開放在 `rules/` 與 `presentation/` 兩個資料夾,但仍在同一個專案裡。

## 遊戲方向

- 一局 30–60 秒的決策型遊戲。
- 不是打敗其他玩家,而是挑戰規則本身。
- 遊戲的重心是讓玩家感覺「剛剛是我自己的決定」。
- 機率存在,但玩家可以影響機率,所以失敗比較像是「我剛剛判斷錯誤」,而不是「運氣太差」。

## 視覺原則

- 盡量用圖像跟動畫取代文字,讓規則被看出來,而不是讀出來。

## 第一版(MVP)範圍

- 三種選擇、五回合、立刻給回饋。
- 成功的指標不是功能齊全,而是玩完一局會不會想再來一局。

## 目前實作狀態

`rules/` 是不依賴場景樹的規則層,可以獨立閱讀、之後也可以獨立測試:

- `round_option.gd` — 單一選項的資料:id、風險(risk)、報酬(reward)、視覺大小提示(size_hint)。
- `game_rules.gd` — 每回合產生三個選項(風險/報酬隨回合遞增),並依「基礎風險 − 玩家影響力」計算成敗。
- `run_state.gd` — 單局進度:目前回合、分數、歷史紀錄。
- `game_session.gd` — 串起以上三者,用 signal(`round_ready` / `round_resolved` / `run_ended`)對外廣播狀態變化;呈現層負責訂閱,並自行決定節奏(例如動畫播完才呼叫 `advance()` 進下一回合)——節奏是呈現層的事,不是規則層的事。

`presentation/main.gd` 是視覺呈現(尚未在 Godot 編輯器中實際開啟測試過,仍是色塊組成,還沒有真正的美術):

- **疊塔**:畫面中央有一座塔,玩家每回合從三個方塊中選一個疊上去。方塊依風險上色(越紅越危險)、依報酬放大——大小與顏色取代文字說明。
- 玩家按住方塊「蓄力」,放開的時機決定影響力(太快或太久都會降低影響力,抓到甜蜜點影響力最高)——這是玩家能實際練習、變準的技巧,而不是單純的機率賭注。
- 成功:方塊閃綠,穩穩疊上塔頂,塔變高。
- 失敗:方塊閃紅,塔跟著往一邊傾斜——失敗次數用「塔的傾斜角度」表達,不需要額外的文字或圖示。傾斜到超過容許次數,塔會整個倒塌(方塊四散、淡出),整局立刻結束。
- 塔的高度就是目前的分數視覺化,傾斜角度就是目前還能承受幾次失敗——單一個物件同時傳達進度與風險,不需要另外的血條或數字。
- 結束畫面依「撐完五回合」或「塔倒了」顯示不同訊息,並附成功次數與再來一局的按鈕。

## 設計決策

文件最初結尾標記了三個「下一步需要定」的問題,目前狀態:

1. **每回合玩家到底在做什麼決定?**(暫定,尚未收到明確回饋)
   選一個風險/報酬不同的方塊疊上塔,並用按住蓄力的時機影響成功率。這是目前實作已經在用的機制,等實際玩過後可能需要調整手感。
2. **玩家追求的是什麼?**(已定案:有限次數失敗)
   允許失敗 `GameRules.MAX_FAILS`(目前是 2)次,超過就整局結束、塔倒塌。介於「五回合一定玩完」跟「一次失敗就結束」之間,保留張力但不會讓手氣差的玩家立刻出局。
3. **這個世界的視覺隱喻是什麼?**(已定案:疊塔)
   從抽象風險方塊換成具體的疊塔——呼應專案本身「three-blocks」的名字,也讓「進度」與「風險」都能用塔本身的狀態(高度、傾斜)直接看出來。

之後如果要再加玩法或特效,應該以「疊塔」為準——例如新的方塊種類、新的疊放方式,而不是重新設計視覺語言。
